# Zenn 記事ライティングガイド

このリポジトリで公開する Zenn 記事の共通ルール。
`article` / `writing-check` / `publish-check` スキルから参照される。

## 対象読者

- **主読者**: 日本語話者のソフトウェアエンジニア。Web アプリケーション開発の基礎知識はある
- **前提知識**: 扱うプロダクト・ライブラリを「名前は聞いたことがある」程度。深い前提は置かない
- **読む動機**: 同じ問題にぶつかって検索してきた / 導入を検討している / 事例を知りたい
- **専門用語**: 一般的な技術用語（HTTP、CI、ORM 等）は説明不要。プロダクト固有の概念（Span、Trace、SKILL 等）は初出時に一行で説明する

## 著者の定型

### 導入

記事の1行目（frontmatter 直後）は自己紹介から始める。

```markdown
こんにちは。PeopleX エンジニアの竹内（[@Kill_In_Sun](https://x.com/kill_in_sun)）です。
```

- 「PeopleX エンジニア」は**半角スペースあり**で統一する（過去記事に `PeopleXエンジニア` の揺れあり）
- 名義は「竹内」を基本とする（過去記事に「首無しキリン」表記あり。カジュアルな記事では併記可）
- 会社を初めて紹介する記事では `[株式会社 PeopleX](https://corp.peoplex.jp/)` とリンクする

自己紹介のあと、2〜4文で「この記事で何を書くか」「誰の役に立つか」を述べる。

### 締め

- 通常記事: `## おわりに` または `## まとめ`
- 外部情報を参照した記事: 末尾に `## 参考` を置き、出典を箇条書きでリンクする

## frontmatter

```yaml
---
title: "記事タイトル"
emoji: "🦒"
type: "tech" # tech: 技術記事 / idea: アイデア
topics: ["Langfuse", "Sentry", "OpenTelemetry"]
published: false
---
```

制約は zenn-cli のバリデーション（`node_modules/zenn-cli` 実装）に基づく。`npx zenn preview` の画面でも確認できる。

| 項目 | 制約 | このリポジトリの慣習 |
|---|---|---|
| `title` | 必須・**70文字以内**・文字列 | ツール名を `[Cursor] 〜` のように角括弧で前置するパターンあり |
| `emoji` | 絵文字**1文字だけ** | 🦒 が定番。内容に寄せる場合のみ変更（例: 📘 ドキュメント系） |
| `type` | 必須・`tech` or `idea` | コメント `# tech: 技術記事 / idea: アイデア` を残す |
| `topics` | 配列・**最大5つ**・すべて文字列・**記号とスペース不可**（`C++`→`cpp`、`C#`→`csharp`） | **Zenn の既存トピック名に正確に合わせる**（表記が違うと別トピック扱いになり流入しない） |
| `published` | 必須・**真偽値**（`"true"` のようにクォートで囲まない） | 新規作成時は必ず `false`。`publish-check` を通してから `true` にする |
| `published_at` | 任意・`YYYY-MM-DD` or `YYYY-MM-DD hh:mm` | 予約投稿する場合のみ。**未来日時を指定するなら `published: true` が必須** |

- `tags` は使わない（`topics` が正しいキー）
- ファイル名（slug）は `a-z0-9` とハイフン・アンダースコアの12〜50字。`npx zenn new:article` が生成する14桁の16進数をそのまま使う

## 文章のルール

### textlint が機械的に見る項目（先に潰す）

`pnpm exec textlint articles/<file>.md` で検出される。人手でレビューする前に必ず通す。

| ルール | 設定 |
|---|---|
| 一文の長さ | 100文字以内 |
| 読点（、） | 一文に3つまで |
| 連続する漢字 | 6文字まで |
| 文体 | 本文は**ですます**、リスト内は**である** |
| 同じ助詞の連続 | 禁止（`no-doubled-joshi`） |
| 弱い表現 | 「〜かもしれない」等の多用を検出 |
| 冗長表現 | 「〜することができる」→「〜できる」等 |
| 全角半角の混在 | アルファベットの混在を検出 |
| 用語統一 | `prh.yml` が唯一の正。用語集をこのガイドに重複させない |

自動修正できるものは `pnpm exec textlint --fix articles/<file>.md`。

### natural-japanese が検出する項目

`pnpm natural articles/<file>.md`（`uv` が必要）で、形態素解析による検出を走らせる。

| 検出対象 | 例 |
|---|---|
| 禁止語・LLM 常套句 | 「のではないでしょうか」「〜と言えるだろう」「正面から向き合う」 |
| 紋切り型フレーズ | 定型的な言い回しの多用 |
| 文リズムの単調さ | 同じ長さ・同じ構造の文が連続する |
| 英語統語の直訳調 | 無生物主語 + 他動詞、連体修飾の過度な入れ子 |

**検出は機械、判断は人間**。語り口として意図的に使っているものまで直さない。

### textlint が見られない項目（人／LLM がレビューする）

1. **結論ファースト** — セクションの冒頭で結論を述べ、経緯は後に置く。「調べた順」ではなく「読者が知りたい順」に並べる
2. **一文一義** — 一文に主張を1つだけ。逆接（が、けれど）で複数の主張を繋がない
3. **一見出し一テーマ** — 見出しが内容を正確に表しているか。1つの見出しに複数のトピックが同居していないか
4. **段落の論理接続** — 段落どうしが「だから」「しかし」「たとえば」のどれで繋がるか説明できるか。繋がらない段落は順序が間違っている
5. **コードブロックの前後** — コードの前に「何をするコードか」、後に「結果どうなるか」を書く。コードだけを置かない
6. **前提知識のギャップ** — 説明なしに使っている固有名詞・略語がないか。読者が前提を持たないと理解できない箇所を特定する
7. **体験談と一般論の分離** — 「自分の環境ではこうだった」と「一般にこうである」を混ぜない。前者は条件（バージョン・構成）を添える
8. **曖昧な表現** — 「適切に」「必要に応じて」「かなり」を具体的な値・条件に置き換える
9. **二重否定** — 肯定形に書き換える
10. **修飾語のスコープ** — 修飾語と被修飾語を近接させる

## Zenn 独自記法

```markdown
:::message
補足・注意事項
:::

:::message alert
警告・重要な注意
:::

:::details 折りたたみの見出し
長いログや設定ファイルの全文
:::
```

- コードブロックにはファイル名を付けられる: ` ```ts:src/index.ts `
- 差分を見せるときは ` ```diff ts `
- 数式は `$$` で囲む（KaTeX）

## 画像

- 配置先は `images/`、記事からの参照は**絶対パス** `/images/<name>.png`
- ファイル名は snake_case。記事ごとのプレフィックスを付けて衝突を避ける（例: `langfuse_pic1.png`, `rancher_desktop_1.png`）
- **alt テキストは必ず内容を書く**。`Alt text` や `image` のようなプレースホルダーを残さない
- スクリーンショットは公開前に `disclosure-check` で中身を確認する

## 見出し構成

- 記事タイトルが H1 として扱われるため、**本文の見出しは `##` (H2) から始める**
- 見出しレベルを飛ばさない（`##` の次に `####` を置かない）
- コードブロック内のコメント行が `#` で始まる場合、見出しと誤認されないよう言語タグを必ず付ける

## 記事タイプ別の構成テンプレート

### A. トラブルシュート型

「想定外の事象が起きた → 原因を突き止めた → こう直した」

```markdown
（自己紹介＋この記事の要約）

## <起きた事象>
何がどう困ったか。可能なら数値・スクリーンショットで示す。

## 原因 - <原因の一言>
調査の過程ではなく、原因そのものを先に書く。根拠となるドキュメント・コードを示す。

## <対処>
実際に入れた変更。コードは差分で示す。

## <効果の検証>
直った証拠。Before/After の数値。

## おわりに
学び。同じ罠を踏みそうな人への注意。

## 参考
```

### B. 技術紹介・導入手順型

「こういう仕組みを作った / このツールを入れた」

```markdown
（自己紹介＋この記事の要約）

## この記事で実現すること
完成形を先に見せる（スクリーンショット・アウトプット例）。

## 全体のアーキテクチャ
図または構成の箇条書き。

## Step 1: <準備>
## Step 2: <実装>
## Step 3: <動作確認>

## 実際に使ってみる
運用してみた所感。

## おわりに
```

### C. 検証・比較型

「A と B のどちらがよいか実際に測った」

```markdown
（自己紹介＋この記事の要約）

## 結論
先に結論を書く。表で示す。

## 前提・検証環境
バージョン、ハードウェア、測定条件。再現に必要な情報をすべて。

## 検証方法
コードと手順。

## 結果
数値と考察。

## どう使い分けるか

## おわりに
```

### D. 事例・ポエム型

「こういう運用をしている / こう考えている」

```markdown
（自己紹介＋この記事の要約）

## <背景・課題>
## <やったこと>
## <結果どうなったか>
## おわりに
```

## セルフチェックリスト

### 構成

- [ ] タイトルが内容を正確に表し、検索されそうな語を含んでいる
- [ ] 冒頭2〜4文で「何の記事か」「誰の役に立つか」が分かる
- [ ] 各セクションが結論から始まっている
- [ ] 見出しが `##` から始まり、レベルが飛んでいない
- [ ] 締め（`## おわりに` / `## まとめ`）がある

### 文章

- [ ] `pnpm exec textlint` がエラーなしで通る
- [ ] 一文に主張が1つだけ
- [ ] 段落どうしの接続が説明できる
- [ ] 曖昧な表現を具体的な値・条件に置き換えた
- [ ] 体験談と一般論を混ぜていない

### コード・図

- [ ] すべてのコードブロックに言語タグがある
- [ ] コードの前に目的、後に結果の説明がある
- [ ] 省略箇所が `// ...` 等で明示されている
- [ ] 画像の alt テキストが内容を説明している
- [ ] 画像ファイルが `images/` に実在する

### 事実

- [ ] バージョン番号・料金・API 名を一次情報で確認した
- [ ] 「〇〇年〇月時点」の記載がある（変化しやすい情報を含む場合）
- [ ] 出典を `## 参考` にリンクした

### 公開可否

- [ ] 顧客名・未公開機能・内部 URL・認証情報が含まれていない
- [ ] スクリーンショットの中に社外秘が写り込んでいない
- [ ] `topics` が Zenn の既存トピック名と一致している
