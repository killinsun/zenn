# テクニカルライティングチェッカー

Zenn 記事の文章品質をチェックする。textlint で機械的な指摘を潰したうえで、
構成・論理・読者視点という機械が判定できない観点をレビューする。

**出力言語: 日本語**

## ワークフロー

### 0. スキル使用の明示

「**writing-check** skill を使います。」と発言してから作業開始。

### 1. 対象記事の特定

以下の優先順で決める。

1. 引数でファイルパスまたは slug が指定されている
2. `git status` / `git diff` に未コミットの `articles/*.md` がある
3. `articles/` の最終更新が最も新しいファイル

複数の候補がある場合はユーザーに確認する。

### 2. ガイド読み込み

`.agents/references/zenn-writing-guide.md` を読み込む。

### 3. textlint 実行

```bash
pnpm exec textlint articles/<file>.md
```

出力を以下に分類して提示する。

- **自動修正できるもの** → `pnpm exec textlint --fix articles/<file>.md` を提案（実行はユーザー承認後）
- **手で直す必要があるもの** → 該当箇所ごとに修正案を出す
- **意図的に無視してよいもの** → 理由を添えて「無視推奨」と明示する（例: コードブロック中の英数字、固有名詞の表記）

textlint がエラーゼロで通るまで、ここで止まらずに次へ進む。機械的な指摘と構成の指摘は同時に出す。

**`prh.yml` が用語統一の唯一の正**。用語の揺れをスキル側の判断で追加指摘しない。
新しい表記ゆれを見つけた場合は「`prh.yml` へのルール追加」として別途提案する。

### 3-2. natural-japanese（AI 臭さ・悪文の検出）

```bash
uv run .agents/skills/natural-japanese/scripts/lint.py articles/<file>.md
```

形態素解析で、textlint が見られない層を検出する。

- 禁止語・LLM 常套句（「のではないでしょうか」「〜と言えるだろう」等）
- 紋切り型フレーズ
- 文リズムの単調さ・段落構造の均質さ
- 英語統語の直訳調（無生物主語 + 他動詞、連体修飾の過度な入れ子）

検出結果は Step 6 の指摘に合流させる。原則 🟢 Low〜🔵 Medium 相当として扱う。

**著者の語り口は残す。** 「のではないでしょうか」が意図的な問いかけとして機能している場合は、
検出されても「意図的なら見送り」と添えて提示する。機械の指摘をそのまま修正指示にしない。

文体を腰を据えて直したい場合は `/natural-japanese` を直接使うよう案内する
（診断・スコアリング・修正が新しい指摘を生まなくなるまでのループが用意されている）。

### 4. 構成レビュー

記事全体を読み、以下を評価する。

| 観点 | 見るところ |
|---|---|
| 導入 | 冒頭2〜4文で「何の記事か」「誰の役に立つか」が分かるか |
| 結論ファースト | 各セクションが結論から始まっているか。「調べた順」に並んでいないか |
| 見出しの粒度 | 見出しが内容を正確に表しているか。1見出しに複数テーマが同居していないか |
| 見出しレベル | `##` から始まっているか。レベルを飛ばしていないか |
| 段落の接続 | 段落どうしが「だから／しかし／たとえば」のどれで繋がるか説明できるか |
| 締め | `## おわりに` または `## まとめ` があるか |

### 5. 読者視点レビュー

| 観点 | 見るところ |
|---|---|
| 前提知識のギャップ | 説明なしに使っている固有名詞・略語。初出時の一行説明があるか |
| コードの文脈 | コードブロックの前に目的、後に結果の説明があるか |
| 体験談と一般論 | 「自分の環境ではこうだった」と「一般にこうである」が混ざっていないか。前者に条件（バージョン・構成）が添えてあるか |
| 曖昧な表現 | 「適切に」「必要に応じて」「かなり」「わりと」を具体的な値・条件にできるか |
| 再現可能性 | 読者が同じことをやるのに足りない情報がないか |

### 6. 指摘の提示

問題ごとに Before/After 形式で提示する。1件ずつ、理由を添える。

```
【結論ファースト違反】L42-58「原因調査」セクション

Before:
> まず Sentry のダッシュボードを開きました。次に Span の一覧を見たところ、
> 大量のイベントが記録されていました。さらに調べていくと、OpenTelemetry の
> 設定が原因であることが分かりました。

After:
> 原因は OpenTelemetry の設定でした。上流に設置した OTel が、LLM に関係しない
> 呼び出しまですべて Span として Langfuse に送っていたためです。
>
> 気づいたきっかけは Sentry のダッシュボードでした。（以下、調査の経緯）

理由: 読者が知りたいのは原因であって調査の順序ではありません。
      結論を先に置き、経緯は「どうやって気づいたか」として後ろに回します。
```

指摘は**重要度順**に並べる。

- 🔴 High: 読者が誤解する・理解できない（結論が見えない、前提説明の欠落、事実と体験の混同）
- 🟡 Medium: 読みにくいが理解はできる（段落順序、見出し粒度、冗長）
- 🟢 Low: 表現の磨き込み（言い回し、リズム）

### 7. 修正の適用

指摘を提示したあと、ユーザーに確認する。

- 「すべて適用」「High だけ適用」「個別に選ぶ」から選んでもらう
- 適用後に `pnpm exec textlint` を再実行し、修正で新たな違反を作っていないか確認する

### 8. 完了報告

```
Done: articles/<slug>.md

textlint: <N>件 → <M>件
構成・読者視点: 🔴<N>件 🟡<N>件 🟢<N>件 → 適用 <N>件 / 見送り <N>件

見送った指摘:
- <内容と理由>
```

## ルール

1. **textlint を先に走らせる**: 機械で分かることを人手のレビューに混ぜない
2. **`prh.yml` が用語の正**: 用語集をスキル側に持たない。追加が必要なら `prh.yml` へのルール追加として提案する
3. **Before/After 必須**: 「読みにくい」だけの指摘をしない。必ず具体的な書き換え案を出す
4. **理由を添える**: どのルールに照らしてなぜ問題なのかを1文で示す
5. **重要度で並べる**: 全部同列に並べない。High から潰せるようにする
6. **著者の声を消さない**: 「〜という話です」「供養（？）として」のような語り口は著者の個性。読みにくさの原因でない限り触らない
7. **勝手に書き換えない**: 承認前にファイルを編集しない
8. **事実は見ない**: バージョン番号や料金の正しさは `fact-check`、コードの動作は `code-verify` の担当。気づいた場合は「要確認」として列挙するに留める
