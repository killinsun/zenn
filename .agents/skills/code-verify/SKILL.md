# コードブロック検証スキル

記事に載せたコードが実際に動くか、書かれている API が現行のものかを検証する。
技術記事のコードは読者がコピーして使うため、**動かないコードは記事の信頼性を直接損なう**。

**出力言語: 日本語**

## ワークフロー

### 0. スキル使用の明示

「**code-verify** skill を使います。」と発言してから作業開始。

### 1. 対象記事の特定

引数指定 → 未コミットの `articles/*.md` → 最終更新が最新のファイル、の順で決める。

### 2. コードブロックの抽出と分類

記事中のすべてのコードブロックを列挙し、分類する。

| 分類 | 例 | 検証方法 |
|---|---|---|
| **実行可能コード** | ts / js / tsx / py / go / rb | 構文チェック → 型チェック → 可能なら実行 |
| **シェルコマンド** | bash / sh / zsh | コマンド・オプションの実在確認（実行はしない） |
| **設定ファイル** | json / yaml / toml / Dockerfile | パース検証、スキーマ準拠 |
| **出力例・ログ** | 実行結果の貼り付け | 検証対象外（分類だけ報告） |
| **擬似コード・断片** | 説明用の抜粋 | 構文チェックのみ。省略の明示を確認 |
| **言語タグなし** | ``` だけ | 🔴 指摘対象。内容から言語を推定して付与を提案 |

一覧を提示してから検証に入る。

```
| # | 行 | 言語 | 分類 | 行数 |
|---|-----|------|------|------|
| 1 | L34 | ts   | 実行可能 | 22 |
| 2 | L67 | （なし） | 不明 | 8 |
| 3 | L88 | bash | シェル | 3 |
```

### 3. 静的検証

**リポジトリを汚さない**。作業はリポジトリ外の一時ディレクトリで行う。

```bash
WORK=$(mktemp -d)
```

- **TypeScript / JavaScript**: 一時ディレクトリに切り出し、`npx tsc --noEmit` で型チェック。import しているパッケージは `npm install <pkg>@<version>` で実際に入れて解決させる
- **JSON / YAML / TOML**: パースして構文エラーを検出
- **シェル**: `bash -n` で構文チェック。使っているコマンド・オプションが実在するか `--help` や man で確認
- **Python**: `python -m py_compile`

依存パッケージのインストールは重い。**記事の主張に関わるコードだけに絞る**か、ユーザーに確認する。

### 4. API 面の現行性チェック

コード中の以下が現行の仕様かを確認する。

- メソッド名・関数名（deprecated になっていないか）
- オプション名・プロパティ名（リネームされていないか）
- import パス（パッケージ構成が変わっていないか）
- パッケージのバージョン（記事が指定しているバージョンが実在するか、大幅に古くないか）

`WebFetch` で公式ドキュメント・型定義・CHANGELOG を確認する。
判定が `fact-check` と重なる場合は、こちらでは「コードとして正しいか」に絞り、仕様の記述内容は `fact-check` に回す。

### 5. 記事としての品質チェック

| 観点 | 見るところ |
|---|---|
| 言語タグ | すべてのコードブロックに付いているか |
| ファイル名注記 | 複数ファイルを扱う記事で ` ```ts:src/index.ts ` を使っているか |
| 省略の明示 | 抜粋の場合 `// ...` や `# 略` で明示されているか。無言の省略はコピペしたときに動かない |
| 差分表記 | 変更を見せる箇所で ` ```diff ts ` を使えないか |
| 秘匿値 | API キー・トークン・実際のエンドポイントが埋まっていないか（詳細は `disclosure-check`） |
| 行数 | 30行を超えるブロックは `:::details` での折りたたみを検討 |

### 6. レポート提示

```
## コード検証結果: articles/<slug>.md

| # | 行 | 言語 | 判定 | 内容 |
|---|-----|------|------|------|
| 1 | L34 | ts | ✅ | 型チェック通過 |
| 2 | L67 | （なし） | 🔴 | 言語タグなし。ts と推定 |
| 3 | L88 | ts | ❌ | `generateObject` の第2引数は現在 `schema` ではなく `output` |

### ❌ 動かないコード
（該当箇所と修正案を diff で）

### 🔴 記事品質
（言語タグ抜け、省略の明示漏れ）

### ⚠️ 検証できなかったもの
（理由: 依存が重い / 外部サービスが必要 / 実行環境が手元にない）
```

### 7. 修正の適用

ユーザー承認後に記事を修正する。検証に使った一時ディレクトリは削除する。

### 8. 完了報告

```
Done: articles/<slug>.md

コードブロック: <N>個
検証: ✅<N> / ❌<N> / 🔴<N> / ⚠️検証不可<N>
修正: <N>件を適用

検証できなかったもの:
- <#N> <理由>
```

## ルール

1. **リポジトリを汚さない**: 検証用の一時ファイル・`node_modules` をリポジトリ内に作らない。`mktemp -d` を使い、終わったら消す
2. **省略＝バグではない**: 記事のコードは抜粋が普通。動かないことを指摘するのではなく、**省略が明示されているか**を見る
3. **検証できなかったものを黙らせない**: 依存が重い・外部サービスが必要で検証できなかったものは、必ず ⚠️ として報告する。「全部確認した」と言わない
4. **実行は慎重に**: 外部 API を叩く、課金が発生する、ファイルを書き換えるコードは実行しない。静的検証に留めて理由を報告する
5. **勝手に書き換えない**: 承認前にファイルを編集しない
6. **役割分担を守る**: 仕様の記述内容は `fact-check`、秘匿値の判断は `disclosure-check`。気づいたら該当スキルへの委譲を促す
7. **コードの意図を変えない**: 動くようにするための修正であって、リファクタリングはしない。記事の説明と乖離させない
