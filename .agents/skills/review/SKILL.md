# review

記事を **5観点で並列レビューし、union（和集合）で統合**する。番号付きテーブルで提示し、
著者が選んだ指摘をその場で修正して、**対応台帳**を残す。

**出力言語: 日本語**

## 設計思想

「著者が1次レビュワー」の核となるスキル。`/publish` の Step で呼ばれるほか、単独でも回せる。

**なぜ並列 union なのか**: LLM レビューは1パスごとに拾う指摘がぶれる。1回だけ回すと取りこぼし、
それが公開後に読者やコメントで顕在化する。観点を分けて並列に当て、**どれか1つでも拾えば採用**する。
多数決ではなく union なのは、狙いが「片方しか気づかなかった本物を取りこぼさないこと」だから。

**責務分離**:

- **知識** = 既存スキルの SKILL.md（`disclosure-check` / `fact-check` / `code-verify` / `writing-check`）と `.agents/references/zenn-writing-guide.md`
- **本スキル** = reviewer 人格（severity 体系・出力フォーマット・規範）を注入し、各観点に「レビュー」を依頼するワークフロー

観点ごとの判断基準は各 SKILL.md が唯一の正。本スキルで再定義しない。

## severity 体系

記事は公開したら取り消せない。severity は**読者と著者が被る損害**で切る。

| severity | 判定基準 |
|---|---|
| **🚨 CRITICAL** | 公開したら取り返しがつかない — API キー・トークンの混入、顧客や個人が特定できる記述、未公開機能の暴露、他者を毀損する記述、明確な事実誤り（誤った手順で読者の環境を壊す類） |
| **⚠️ HIGH** | 読者に実害が出る — コピーしても動かないコード、現行と食い違う仕様・料金・バージョン、結論が読み取れない構成、前提知識の説明が欠落して再現できない、出典のない断定 |
| **🔵 MEDIUM** | 読みにくいが理解はできる — 段落順序、見出し粒度、冗長表現、AI 臭い言い回し、体験談と一般論の混在、コードブロックの前後説明の欠落 |
| **🟢 LOW** | 磨き込み — 言い回し、表記、リズム |

> **線引きの注意**: 「この表現はもっと良くできる」は MEDIUM 以下。HIGH は「読者が困る」ことが説明できる場合のみ。
> ここを取り違えると `/publish` のゲートが過剰に鳴って形骸化する。

## 起動構成

### 事前の機械チェック（agent 起動と独立・先に実行）

| チェック | コマンド | 扱い |
|---|---|---|
| 記事の機械検査 | `node scripts/validate-articles.mjs --json <file>` | `secret` ルールのヒットは 🚨 CRITICAL に直行。他は結果に応じて HIGH / MEDIUM |
| textlint | `pnpm exec textlint <file>` | 🔵 MEDIUM（自動修正可能なものは `--fix` 案内） |
| AI 臭さ・悪文 | `uv run .agents/skills/natural-japanese/scripts/lint.py <file>` | 🔵 MEDIUM。禁止語・紋切り型・文リズムの単調さ・翻訳調を形態素解析で検出する |

機械が出した指摘は agent に投げ直さない。そのまま union に混ぜる。

> `natural-japanese` は文体の深い推敲までできるスキル。本スキルでは `lint.py` の検出だけを使う。
> 腰を据えて文体を直すときは `/natural-japanese` を直接使うよう案内する。

### 並列レビュー（agent）

| lens | 知識source | 起動条件 |
|---|---|---|
| **disclosure** | `.agents/skills/disclosure-check/SKILL.md` | **常時（必須）**。業務ネタでなくても回す |
| **fact** | `.agents/skills/fact-check/SKILL.md` | 常時 |
| **code** | `.agents/skills/code-verify/SKILL.md` | コードブロックが1つ以上ある場合 |
| **writing** | `.agents/skills/writing-check/SKILL.md` + `.agents/references/zenn-writing-guide.md` | 常時 |
| **reader** | `.agents/references/zenn-writing-guide.md` の「読者視点」節 | 常時 |

- **disclosure は必ず起動する**。このリポジトリは PUBLIC なので、`published: false` でも push した時点で誰でも読める
- **reader** は他 lens と違い専用スキルを持たない。「その分野を知らない読者が、この記事だけで再現できるか」に特化させる
- マッチしない lens は起動しない（コードがなければ code は回さない）

## reviewer 人格（各 agent への注入プロンプト）

```
Caller: /review

あなたは Zenn 技術記事の「{lens}」観点のレビュワーです。

対象記事: {file}

まず以下を読み、そこに書かれた判断基準に従ってレビューしてください。
- {知識source のパス}

【severity 体系】
- 🚨 CRITICAL: 公開したら取り返しがつかない（秘匿値、顧客・個人の特定、未公開機能、明確な事実誤り）
- ⚠️ HIGH: 読者に実害（動かないコード、現行と食い違う情報、結論が読めない、前提説明の欠落、出典なき断定）
- 🔵 MEDIUM: 読みにくいが理解可能（段落順序、見出し粒度、冗長、AI臭さ、体験談と一般論の混在）
- 🟢 LOW: 磨き込み（言い回し、表記、リズム）
- ※「もっと良くできる」は MEDIUM 以下。HIGH は「読者が困る」と説明できる場合だけ。

【出力フォーマット】
## {lens} 結果

🚨 CRITICAL (N件)
- L{行番号} — 指摘 / 根拠 / 修正案

⚠️ HIGH (N件)
- ...

🔵 MEDIUM (N件)
- ...

🟢 LOW (N件)
- ...

【規範】
- 網羅的に拾う（MEDIUM / LOW も含む）。取捨選択は著者の責任
- 行番号を必ず付ける
- 根拠を示す（ガイドのどの原則か、どの一次情報か）
- 修正案は具体的に。「読みやすくする」ではなく書き換え後の文を出す
- 挨拶・締めくくり・サマリは省く
- 担当観点の外には踏み込まない（他 lens が並列で見ている）
- 著者の語り口（「〜という話です」「供養（？）として」等）は個性。読みにくさの原因でない限り触らない
- 0件なら「{lens}: 指摘なし」だけ返す

全 severity を返してください。
```

## ワークフロー

```
1. 対象特定 → 2. 機械チェック → 3. 起動計画 → 4. 並列レビュー(人格注入)
                                                        ↓
                                        5. union集約(重複統合)
                                                        ↓
      8. 対応台帳 ← 7. 詳細展開/選択→その場修正 ← 6. 要点出力(severity別テーブル)
```

### 0. スキル使用の明示

「**review** skill を使います。」と発言してから作業開始。

### 1. 対象記事の特定

引数指定 → 未コミットの `articles/*.md` → 最終更新が最新、の順。複数候補ならユーザーに確認。

### 2. 機械チェック

「起動構成」の3コマンドを実行する。`secret` ルールのヒットがあれば、**この時点で著者に警告する**
（既に push 済みなら、履歴からの除去とキーのローテーションが必要になるため）。

### 3. 起動計画

記事にコードブロックがあるかを確認し、起動する lens を確定する。

### 4. 並列レビュー

確定した lens を **1バッチで並列に Agent 起動**する。各 agent には上記の人格プロンプトを注入し、
`{知識source のパス}` を lens ごとに差し替える。

### 5. union 集約

1. 各指摘を `{severity, 行, 指摘の本質, 根拠, 修正案, 出所}` に整形する
2. **重複統合**: 行が近接（±3行）していて問題の本質が同じものは1件にまとめ、出所を `[via writing + reader]` のように併記する
3. **片方しか出していない指摘も必ず残す**（union の主旨）
4. severity は統合対象の最も高いものを採用する（次の較正で確定）

### 6. 較正と要点出力

**較正**: CRITICAL を1件ずつ実記事と照合し、根拠が確認できないものは HIGH に降格する。
HIGH のうち「既に書いてあるがもっと良くできる」だけのものは MEDIUM に降格する。
**疑わしきは維持**（見落としのほうが高くつく）。新規指摘はここで足さない。

出力は severity ごとの見出し + テーブル。**全指摘に通し番号**を振る。

````
# /review 結果  articles/<slug>.md
🚨1 ⚠️3 🔵5 🟢2
最優先: No.1 Slack スクショに発言者名（L88 の画像）

### 🚨 CRITICAL
| No. | 箇所 | 要点 | 修正案 |
|:--:|---|---|---|
| 1 | `L88` | Slack スクショに同僚の表示名とアイコン | 該当部分をマスキングするか、本文で要約して画像を外す |

### ⚠️ HIGH
| No. | 箇所 | 要点 | 修正案 |
|:--:|---|---|---|
| 2 | `L42` | Langfuse の無料枠が現行と違う | 月3万イベントに修正し「2026年8月時点」を添える |
| 3 | `L67` | generateObject の引数名が旧仕様 | schema → output に変更（v4 で改名） |
| 4 | `L15` | 結論が第3段落まで出てこない | 「原因は OTel の設定でした」を節の冒頭に移す |

### 🔵 MEDIUM
| No. | 箇所 | 要点 | 修正案 |
|:--:|---|---|---|
| 5 | `L23` | 「のではないでしょうか」（LLM 常套句） | 「〜なケースが多いはずです」等に置換 |
...

詳細を見たい番号 / 直したい番号を指定（例: 詳細 1,3 ／ 直す 1,2,4 ／ none）。
````

ルール:

- **1指摘1行**。要点は20〜30字の体言止め。込み入った根拠は「詳細 N」で展開する
- **0件の severity は見出しごと省略**
- 番号は `No.N` 形式。`#N` は使わない（GitHub が無関係な issue にリンクする）
- 指摘0件なら `🎉 指摘なし` だけ表示して終了

### 7. 詳細展開 / その場修正

- **`詳細 1,3`** → その番号の根拠・修正案・出所をフル展開する
- **`直す 1,2,4`** → Edit でワーキングツリーに反映する。修正前に変更内容を要約して示す
- **`none`** → 修正せず台帳だけ残す

規律:

- **コミット・ステージングはしない**（`/publish` または著者の明示依頼に委ねる）
- 画像のマスキングは行わない。位置を指摘するに留める
- 修正が他の指摘に波及する場合は知らせる
- 見送るものに理由があれば添えてもらい、台帳の `wontfix` に使う

### 8. 対応台帳

```
## 記事レビュー対応状況

- [fixed]    No.1 🚨 L88 — Slack スクショを差し替え
- [fixed]    No.2 ⚠️ L42 — 無料枠を月3万に修正、時点注記を追加
- [wontfix]  No.5 🔵 L23 — 「のではないでしょうか」（理由: 語り口として意図的）
- [deferred] No.7 🔵 L104 — 図解の追加（理由: 別途作図してから）
```

- `fixed` = この場で修正 / `wontfix` = 見送り（**理由必須**） / `deferred` = 後回し
- **`/publish` から呼ばれた場合**: この台帳ブロックをそのまま返し、コミットメッセージへ埋め込ませる
- **単独起動の場合**: ターミナルに表示するのみ
- **CRITICAL を `wontfix` にする場合は強く警告する**。`/publish` のゲートは台帳に関わらず CRITICAL を独立に再検査する

## ルール

1. **知識は既存 SKILL.md が正** — 観点ごとの判断基準を本スキルに重複定義しない。本スキルは人格注入とワークフローの担当
2. **union で取りこぼさない** — 片方の lens しか出さなかった指摘も残す。多数決にしない
3. **disclosure は常時起動** — PUBLIC リポジトリなので `published: false` でも push で公開される
4. **機械チェックを先に回す** — validate-articles.mjs / textlint / natural-japanese で拾えるものを agent に探させない
5. **収集は網羅・表示は要点** — agent は MEDIUM / LOW も拾い、著者への表示は1指摘1行に圧縮して番号指定で展開する
6. **severity を膨らませない** — 「もっと良くできる」は MEDIUM 以下。HIGH の乱発はゲートを形骸化させる
7. **修正はワーキングツリーまで** — `git add` / `git commit` はしない
8. **台帳を必ず残す** — fixed / wontfix / deferred。CRITICAL の wontfix は警告する
9. **著者の語り口を消さない** — 均質な文章にするのが目的ではない
