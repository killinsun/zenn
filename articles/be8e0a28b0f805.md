こんにちは。PeopleX エンジニアの竹内（[@Kill_In_Sun](https://x.com/kill_in_sun)）です。

皆さん、AI を使って開発してますか？していますよね？もうこれがないと開発できないというほど世の中の状況は変わってしまいました。
書くよりも、読む時間のほうが圧倒的に長い。まだコードレビューをする現場も大半だと思いますが、そうなってくると読む物量もめちゃくちゃ多いので大変ですよね。

僕は今年５月終わりぐらいから今の開発環境に限界を感じ始めていました。巷では Crit や Zed のようなツールも出ていますし、世の中はもう「読む特化」にシフトしていると。

そこで今回の記事では「究極のコードレビュー環境」を目標に、Neovim へ移り、愛用している自作プラグインと開発・レビューフローを紹介します。

## なぜ IDE をやめたのか

IDE、エディタ遍歴でいうと VSCode -> JetBrains系IDE -> Cursor と辿ってきましたが、オーバースペック感とマウス移動での煩わしさ、そして「どのウィンドウでどのワークツリー、プロダクトのリポジトリを開いているかわかりにくい」という課題を感じていました。

VSCode系エディタであれば code-workspace ごとにエディタの色は変更できますが、git worktree を切って開発する機会が多いとそれも面倒です。

また、エディタ内蔵のターミナルコンソールを使う事って今ほとんどないですよね？一時期前は使ってましたが、今ってもうペインやタブ、めちゃくちゃ開く前提じゃないですか？それにちょっと昔は あのターミナルで Claude Code を使っているとメモリを大量に使うので Ghostty を使ったほうがいいみたいなトレンドもあったりして、エディタで使ってるのってファイルツリーと Git Diff ぐらいなもんなのでした。

それでも LSP によるコードジャンプや定義の確認、参照の一覧など便利な機能は多かったのでしばらくは我慢してましたが、「もうターミナル上で操作すれば切り替えの手間なくて良いのでは？」と考えて結果的には後述の構成に落ち着きました。

### 今のところの構成

- 仮想ターミナルアプリ: Ghostty
- ターミナルマルチプレクサ: herdr
- エディタ: Neovim


### 目指したもの

とはいえ、そのまま入れても Neovim のパワーを100%発揮できないですし、自分のやりたい事は「AIや他の人が書いたコードをしっかり読める」をマストとしていたので、以下のようにしたいと考えました。

- LSP の機能がしっかり使える（コードジャンプ、定義移動、参照元の一覧と移動など）
- コーディングAI やPR作者へのコメントをターミナルから離れずにできる
- PR の変更を、ファイル順ではなく **意味のある順番や塊**  で読める
- 気づいたことをその場のメモとして残せる。しかも commit を汚さない
- ぱっと読んでわからないところをその場でAIにサクッと聞ける

ざっとこんな感じですが、６月入った頃ぐらいの当時の私は Crit という便利なツールの存在も知らなかったので、メモを残す（＝後述のアノテーション機能）やPR差分のファイル一覧を意味のある順番に読める、などは「うっほ！めっちゃいいこと考えたぞワシ！」ぐらいの気持ちでいましたが、６月下旬には社内でもCritが話題になり始め、すでに世の中「読む特化」の環境にシフトしていっているのを感じました。

## 今のところの流れ

1. `prw` コマンドでレビューできそうな PR 一覧を出して選択（自分にアサインされている GitHub Issue から始める場合は `isw`）
2. 選択するとコマンドが自動で Git worktree を切り、初期セットアップ
3. nvim を起動し、自作プラグイン **storyline.nvim** でレビューするべき順番でファイルを塊（チャプター）に分割するので、１つずつ確認
4. 読んでいる時に「GitHub PR 上でレビュイーにコメントしたいな」とか「AIに指示するためにこのコードについてメモ残したいな」というところがあれば **code-annotations**プラグインでコードにメモを残す。言語機能のコメントと異なり、ファイル編集ではなくアノテーションなのでファイルに直接保存されない
5. また、読んでいるメソッドや変数、処理そのものについては**code-ask**プラグインで軽量AIに質問してサッと回答してもらう
6. あらかたコードが読み終わったら **code-annotations** でコメントした内容をAIに指示したり、プルリクエストにコメントをそのまま反映してもらったりする

`prw` と `isw` は `.zshrc` に書いた自作の zsh 関数です。`gh pr list` の結果を fzf で選ぶと、その PR 用の worktree を `git worktree add` して `gh pr checkout` まで済ませて移動します。

## 構成の全体像

設定は `~/.config/nvim` に Lua で置いています。プラグインは明示指定が21個、依存を含めると27個。うち3個は自作です。

```
~/.config/nvim
├── init.lua                # options → keymaps → autocmd → lazy → lsp
├── lua/config/             # 素の設定（options, keymaps, autocmd, lsp, git, telescope_lsp）
├── lua/plugins/*.lua       # 1ファイル1プラグイン（lazy.nvim の import 方式）
├── after/ftplugin/         # markdown だけ
└── after/lsp/              # lua_ls, ts_ls の vim.lsp.Config
```

ここから先は「レビューで実際に効いているもの」だけを、プラグインと自作設定の単位で紹介します。

## storyline.nvim（自作プラグイン）

PR の diff を AI が「意味のある塊（チャプター）」に分解して、順番に読ませてくれるプラグインです。自作3つのうち、一番作り込んだのがこれです。

[storyline.nvim](https://github.com/killinsun/storyline.nvim)

![storyline.nvim の動作。PR を選ぶと AI が変更を解析し、左サイドバーに5つのチャプターと配下のファイルが増減行数つきで並ぶ。選んだチャプターの概要と読むポイントがフロートで表示される](/images/nvim_review_storyline_demo.gif)

### 機能1 - PR の diff をチャプターに分解する

AI（Claude Code / Codex CLI / Cursor Agent を切り替え可能）が diff を解析し、チャプター構成を生成します。左のサイドバーに「チャプター見出し + そのチャプターで読むファイル」が GitHub の PR ツリー風に並びます。

チャプターを選ぶと「概要と読むポイント」がフロートで出るので、そこを読んでから本文に入れます。

### 機能2 - 実ファイルを開いているので `gd` / `gr` がそのまま効く

僕がずっと GitHub 上の Diff view で不便だと思ってたのが、あの画面だとこの関数がどこに定義されてるのか、またどこから呼ばれてるのかって辿りにくいんですよね！
レビュー中に一番やりたいのはまさにそれだったので、この storyline は diff 表示を gitsigns ベースにして、実ファイルのバッファを開いたまま変更行を見られるようにしています。

### 機能3 - 省略なしで全部開いて読む

ファイルの量によっては、変更がないところって省略されちゃってたりもありがちだと思うんですけど、私はあれ全部開いて省略なしの状態で読みたい派なんですよね。
`zr` で全部開いてくれるので、めっちゃ便利です。

### 機能4 - unified / split をその場で切り替える

ファイルによっては unified view と split view どちらで読みたいかも異なってくるので、そのたびに GitHub でいう「表示設定」から切り替えをしなくてはいけなかったんですが、 `<leader>gl` で即座に切り替えができます。これも愛用しています。

![GitHub の PR レビュー画面の表示設定メニュー。Unified と Split を切り替えられる](/images/nvim_review_github_layout_menu.png)

これを nvim の中でやると、こうなります。

![storyline のメインペインが、1枚の unified 表示と左右に分かれた split 表示のあいだで切り替わる](/images/nvim_review_layout_toggle.gif)

なお Diffview を単体で開いているときも、同じ `<leader>gl` で切り替わるようにしています。ビューごとにキーを覚え直したくなかったからです。

### 機能5 - 自然言語でストーリーを組み替える

`A` を押すと、チャプター構成を自然言語で再編できます。

- 「この PR の一番キーとなるものでまとめて」
- 「リクエストごとに controller や resolver から辿れるように」

AI が最初に出してくる構成が、必ずしも自分の知りたい順とは限りませんよね。自分が読みたい切り口を指定できるようにしました。

ちなみに`a` を押せばチャプターについて質問もできます。

### 機能6 - PR と関係なく、機能単位で組み立てて読む

ここまでPR読むのが便利になってくると、既存機能のコードリーディングをするときにも活用したくなってきます。
そこで登場するのが、 `:StorylineRead` という PR ではなく既存のコードを読むモードです。AI が切り口（トピック）を提案してくれるので、チャットで選ぶとそのトピックでコードが構造化されます。

:::details そのほかの機能
- 読了トグル（`m`、`✓` / `·`）と進捗の永続化
- キャッシュキーは変更ファイル集合ベース（当初は diff の全文をキーにしていた）
- `gh` で PR base を自動検出。`pick_base` で picker を差し替え可能
- which-key があればサイドバーで `<Space>` を押すと操作の一覧が出る
- `:checkhealth storyline` に対応。plenary busted でテスト
:::

## code-annotations.nvim（自作プラグイン）

コードに「消えないメモ」を貼るプラグインです。

今まで Claude Code のチャット欄に「〇〇〇ファイルの XXXX メソッドについて…」とか質問したり、修正の指示をしてたりしてたんですが、言及する場所が多いといちいち書くのも面倒くさいですよね。
コードを読みながら気になったところにメモを残せます。自分用のメモとして使ってもいいし、AI への質問や指示に使ってもいいし、PR のコメント下書きにしてもいい。ファイルを書き換えないので、コードに影響なく記録を残せます。

[code-annotations.nvim](https://github.com/killinsun/code-annotations.nvim)

### 機能1 - ファイルを編集せずにメモを貼る

`<leader>an` でカーソル行やビジュアル選択にアノテーションを追加します。extmark で描画しているので、**行を編集してもメモが追従します**。

永続化はプロジェクトごとの sidecar JSON（`~/.code-annotations/<project-slug>/annotations.json`）なので、ソースツリーは一切汚しません。

### 機能2 - 同じシンボルの全出現に同じメモが出る

作っていて一番おもしろかった機能です。

アノテーションは行そのものにも貼れますし、変数そのものにも貼れます。

変数に対してアノテーションをつけると、LSP の `textDocument/definition` でカーソル下シンボルの定義位置を解決し、`textDocument/references` で全参照を取得します。すると「ある変数にアノテーションをつける」だけで、その変数が出てくるすべてのファイル・行に同じメモが表示されるようになります。

行番号ではなく定義の位置をキーにしているので、コードが動いてもメモは付いてきます。

### 機能3 - メモをまとめて AI に渡す

`<leader>ax` で、未解決のアノテーションをコードスニペット付きでエクスポートします。出力をそのまま AI に渡して指示を出せます。

![code-annotations.nvim の動作。テストコードの行にアノテーションを書き込むと、ファイルを編集せずにその行の脇へメモが表示される](/images/nvim_review_annotations_demo.gif)

:::details そのほかの機能
- 解決 / 未解決のトグル（`<leader>ar`）、削除（`<leader>ad`）
- 一覧（`<leader>al`、Telescope が無ければ quickfix）
- `<leader>k` の hover にフックして、LSP の型情報と自分のメモを同時に表示
:::

## code-ask.nvim（自作プラグイン）

行や選択範囲について CLI エージェントに質問して、答えをその場に表示するプラグインです。

コードを読んでいる途中で、別ウィンドウのチャットに移動したくありませんでした。

[code-ask.nvim](https://github.com/killinsun/code-ask.nvim)

### 機能1 - 聞くと、コードの真下に回答が出る

`<leader>aq` でカーソル行、ビジュアルモードなら選択範囲について質問します。答えは **virt_line でコードの真下にアンカー**されるので、視線を動かさずに読めます。`vim.system` で非同期に実行しているのでエディタは固まりません。

![code-ask.nvim の動作。メソッドについて質問すると、数秒後にコードの真下へ回答がインラインで表示される](/images/nvim_review_codeask_demo.gif)

### 機能2 - エージェントとモデルを差し替える

print モードがあれば何でも使える設計にしました。現在は Cursor Agent（`agent -p --trust`）で、`<leader>am` のモデル picker から Sonnet 5 / Sonnet 5 Thinking / Composer 2.5 / Composer 2.5 Fast を切り替えています。

`cmd` / `cmd_args` / `mode` / `workspace` / `answer_guide` がすべて設定できるので、claude や codex でも動きます。

## 似たようなことを、いろんな人がやり始めている

つい先日ですが、[@hiro_o918](https://x.com/hiro_o918) さんも `rinkaku` という自作の CLI ツールを公開されていました。

https://www.m3tech.blog/entry/rinkaku-pr-review

差分をそのまま並べるのではなく、変更されたシンボルのシグネチャと依存関係から先に「輪郭」を掴ませるアプローチです。依存順に並んだファイルツリー、`gd` / `gr` でのジャンプ、メモを AI への指示にまとめる機能まで揃っています。

冒頭で触れた Crit や Zed もそうですが、それぞれ別の場所で別の作り方をしているのに、たどり着く機能が似てくるのがおもしろいところです。やはり全体のトレンドとして「読む特化」にシフトしていて、みんな同じところで困っているんだなと思います。

## おわりに

今のところ、ターミナルメインで開発やレビュー作業ができるようになってとても快適です。ブラウザーに切り替えたりするとどうしても集中が削がれてしまう感覚があったので、それがなくなったのは良いなと感じます。

これから同じ環境を目指したい人は、私の作ったプラグインをそのまま使うでもいいですし、オリジナルで作るのもまた勉強になって良いと思います。この手のプラグインは自分専用に振り切れるので、バイブコーディングでも案外なんとかなってしまいますね。

いずれはコードレビューすらいらない未来が来るとは思っています。ただ私のチームでは、レビューを通したコード理解や技術力の向上も大事だと捉えています。さらにエンタープライズ向けのプロダクトなので、良い品質で提供し続ける責任もあります。しばらくはコードをじっくり読むことから離れられないと思っています。

PeopleX ではこんな感じで自分の環境をカスタマイズしたり、他のメンバーからの知見も活発に飛び交う環境なので、興味あったらぜひカジュアル面談申し込んでいただければと思います。

まだそこまでの気持ちがなくても、私や会社のSNSアカウントをフォローしてウォッチしていただくでも大丈夫です。

また次回をお楽しみに。
